## 2. Where the code differs from SPEC.md

### Code defects

- D1 to D8 of the summary.
- **`exits.ibguard_step`** exists only for the tests: the overlay uses `_ratchet` and its own level checks, and `the_vectors_as_path_points_give_the_same_exits` already proves the vectors through the overlay. A second implementation of the level rule is dead code in a pure module (see §6).
- **`markets.DATA_START_YEARS`** duplicates `jobs.DATA_YEARS` (both 31); only the jobs constant is used. §4.1 belongs to `markets.py`.

### Spec ambiguities (the code follows a reading; the owner decides)

- **Reversal lines in trade mode** are always REFUSED: one line SELLs the long and the short together, and §15.5 refuses "a reducing line [that] would trade more than the position". §14.2 never splits a reversal into a reducing and an increasing line. A strategy with `allow_short` can therefore never reverse live (and, with D1, lifts ibguard's protection when it tries).
- **Absolute price levels on adjusted bars** depend on later corporate actions (§6.3 back-adjusts from the latest data, intentionally). See §3.
- **The risk-free rate a strategy reads** at bar t is DTB3 "on or before" day t (§12), which FRED publishes the next business day. See §3.
- **§15.5 "startup sync complete"**: `precheck` checks the connection and the account; ib_async completes its own sync (positions, orders) inside `connectAsync`, and btlab's recovery runs in `on_connect` before `connect()` returns. A confirmation cannot overtake recovery in practice, but nothing checks it explicitly.
- **BATCH_READY** is emailed for every generated batch, also one without a single PROPOSED line.
- **A busy LIVE lane** drops a follow-up (D8); §17.2 does not say whether follow-ups queue.
- **Readings recorded in earlier plans**, all implemented and tested as written there: the (0, 2] factor applied net of the share ratio (prompt 4); US cash dividends with detail DIV_RESULT (3); CASH_IN_LIEU as an extra exit reason not in §10.8's list (6); one commission per symbol and fill moment (6); a due MAX_HOLD wins over the strategy's order (7); sample deviations for Sharpe, α and β (8); the benchmark takes the run's fill timing and lot setting (8); vol-inverse weights summing to selected/top_k (9); NEEDS_CONFIRMATION recorded as JOB_CANCELLED (14); every symbol failed is FAILED, not PARTIAL (14); market defaults travel with `GET /api/strategies` (17); a minute-bar timeout is FAILED, not EMPTY (21); virtual shorts pay dividends but no borrow fee (22); ibguard's and spylead's payload shapes, which the owner checks against their APIs (20, 23).
- **The session value** is an HMAC of the web token (§19): logout clears the cookie on that device, but the value stays valid wherever else it was stored until the token changes.

## 3. Look-ahead: paths by which a value could come from after the bar it acts on

### Evidence that signals and fills are causal

- **Indicators, features and operands**: computed from rows up to t; proven by truncation tests that alter or remove bars after c (`test_registry.py`: bars_after_c_change_nothing_up_to_c, days_after_c_change_no_feature_up_to_c; `test_builtins.py`: bars_after_c_change_no_target_up_to_c, dca_fills_up_to_c_ignore_later_bars; `test_rules.py`: daily_rules_are_truncation_invariant, minute_rules_are_truncation_invariant; `test_spylead.py`: a_rule_on_a_series_reads_nothing_after_its_bar).
- **Daily values on minute timelines** come from the previous session (§8.4; `test_features.py`, `test_rules.py`).
- **Fills follow the signal**: NEXT_OPEN fills at the next tradable bar's open (`test_engine.py`: next_open_fills_at_the_next_open_with_slippage; `test_intraday.py`: next_open_fills_at_the_next_bar_and_across_sessions); warm-up bars never trade (warm_up_bars_do_not_trade).
- **Plugins**: event-driven `ctx` exposes read-only rows up to t (`test_plugins.py`: ctx_sees_only_rows_up_to_t_and_cannot_write_them); vectorized plugins go through the 5-cut check (a_plugin_that_reads_one_bar_ahead_is_flagged_and_an_honest_one_is_not).
- **Optimization**: OOS picks the best on the first 70% only, and window runs use earlier data as warm-up only (`test_optimize.py`: the_out_of_sample_check_splits_at_70_percent, a_window_run_equals_a_backtest_of_its_period, walk_forward_windows_train_three_years_and_test_one).
- **Live batches** replay through the latest stored session, size on its last close, and fill on the next session's bar (`test_live.py`); LIVE_DATA_INCOMPLETE stops a batch when a symbol lacks the latest session.
- **Minute normalization** uses later share ratios only to restore raw prices as traded; no signal reads them.

### Paths that remain

1. **Back-adjusted absolute levels.** An adjusted price at t is the raw price times the product of factors of every event after t. Ratios, crosses, returns, RSI, z-scores and the like are unaffected, but anything comparing an adjusted level with a constant is not: a rule `PRICE > 50` or `SMA(20) > 100`, ATR, STDEV or VWAP against a fixed number, a plugin threshold on `bars.close`. A future split or dividend changes those signals before it happens. The truncation tests alter bars only, never actions after c, so they do not see it. Prompt 4's plan flagged this for the owner. Options: accept and document it in the rule builder; offer raw-price operands; or validate that constants are compared only with scale-free operands.
2. **The risk-free rate.** `bars.rf` (plugins) and DUAL_MOMENTUM's hurdle read DTB3 of day t at t's close; FRED publishes day t's value on t + 1, and for Taiwan, whose close comes before New York's open, the value is not even set. The effect is tiny (a slow series, compounded over 252 bars), but it is one day of look-ahead in a trading decision. Fix: lag the strategy-facing rf by one day (metrics may keep §12's definition).
3. **Bar-level modelling, by design**: the daily path's order (low first on an up bar) is chosen from the bar's own close; a bar's tradability (volume 0, the TW limit lock) uses the whole bar, including for an order at its open; SAME_CLOSE fills at the close that produced the signal (labelled optimistic). These are intrabar assumptions of §6.5 and §10.8, not data from a later bar.
4. **The vectorized look-ahead check is a heuristic**: 5 cuts, and in an optimization only for the first and the best combination. A plugin that peeks only near the end of the data, or only under other parameters, can pass it.
5. **spylead's one-sided series** are aligned by calendar day on the premise of §5.6 that day d's value uses data released by the previous month end; btlab cannot verify that premise. F and COMPOSITE are in-sample by definition and flagged.

## 4. Orders btlab could send, modify or cancel when it should not

### Evidence of the guarantees

- **Test mode never constructs the order adapter** and connects read-only: `__main__._trader` is built only in trade mode (`test_cli.py`: only_trade_mode_constructs_the_order_adapter; `test_ib.py`: the_link_connects_once_read_only_in_test_mode_with_the_configured_client_id). The web's cancel route refuses in test mode.
- **Only `ib_orders.py` calls `placeOrder` and `cancelOrder`, and nothing calls `reqGlobalCancel`** (`test_trading.py`: only_ib_orders_places_or_cancels_and_nothing_cancels_globally).
- **Foreign orders**: `IbOrders.cancel` acts only on this client id's open trades whose `orderRef` starts with `btlab:`; recovery ignores other orders and records an unmatched `btlab:` one without touching it (cancelling_touches_only_btlabs_own_working_orders, the_order_adapter_maps_tickets_and_cancels_only_its_own_btlab_orders, recovery_matches_the_exact_order_ref_and_leaves_other_orders_alone).
- **Limits** apply at generation and again before sending; trade mode refuses to start without them (the_send_function_refuses_and_the_limits_apply_again, trade_mode_without_limits_names_every_limit).
- **Preconditions**: connected on the configured account, before the cutoff, IB's positions unchanged (BATCH_STALE); a read-only API stops the batch (changed_positions_make_the_batch_stale_and_the_cutoff_ends_it, a_read_only_api_stops_the_batch).
- **Duplicates per contract**: the send function refuses a line while another btlab order works on its contract; a batch is sent once, since confirmation needs PROPOSED; the `orderRef` is stored before `placeOrder`, so a crash after placing is recovered by exact `orderRef` and a line never placed ends EXPIRED at the sweep, never re-sent.
- **ibguard races**: sells skip while ibguard exits or cannot be reached; exclude, verify EXCLUDED, then send; the owner's own exclusions are kept (the_sell_protocol_skips_or_keeps_the_owners_exclusion, an_unreachable_ibguard_skips_sells_but_not_buys).

### Paths found

- **D1**: a refused reducing line leaves ibguard's protection lifted for good (every reversal triggers it).
- **D2**: a confirmed trade-mode batch that never sends (the safe direction, but silent and stuck).
- **D3**: a second batch for an already confirmed session; in trade mode its lines on other contracts go out, and the per-session count limit counts per batch.
- **D5**: after an exception mid-send, the batch and its unsent lines stay CONFIRMED; nothing re-sends them (safe), but they never end.
- **D7**: a dropped link at restore time reads as a closed position, so protection is not restored.
- **Crash window**: ibguard excludes the position before btlab stores the exclusion row; a crash between the two (one state read and one insert) leaves an exclusion btlab does not know about and never restores. Storing the row first (as pending) and resolving it at the sweep would close the window.

## 5. Keys, tokens, the session value and the SMTP password

### Evidence that none of them leaks

- **Logs**: every handler of the root logger uses a redacting formatter (`api_key=`, `token=`, `Authorization` values masked, tracebacks included); no log call formats a key (`test_cli.py`: log_lines_are_redacted; `test_http.py`: log_lines_hold_no_url_key_or_token). Request logs name a label, never a URL; FRED's key travels in `params`, never in a logged string. aiohttp's access log prints request lines, and no btlab route takes a secret in its query.
- **Errors**: `SourceError` texts are built from labels and status codes; aiohttp exceptions contribute only their type name (`test_http.py`: a_source_error_never_holds_a_url_or_a_secret; each client's errors_and_log_lines_hold_no_* test). An unexpected job error passes through `redact` before it reaches an event or an email; an unexpected handler error records only the method, the path and the exception's type, and answers a fixed text.
- **Responses**: the state document shows each key as a boolean only; login answers 401 without echoing anything; the session value appears only in `Set-Cookie` (HttpOnly, SameSite=Strict, Secure behind HTTPS) (`test_web.py`: no_secret_reaches_logs_events_answers_or_errors, the_session_cookie_flags).
- **Config**: printing a config shows no secret; validation messages never quote a value (`test_config.py`: printing_a_config_shows_no_secret, no_message_quotes_a_value_of_the_file).
- **SMTP**: the password reaches only `smtplib.login`; a failed send logs the exception's type only (`test_notifier.py`: a_failed_send_raises_nothing_and_logs_no_secret).
- **spylead and ibguard tokens** go only in the login body; their session cookies live in memory (`test_spylead.py`: a_refused_token_fails_without_showing_the_token_or_the_address).
- **The launcher log** (`%LOCALAPPDATA%\btlab\launch.log`) holds paths and exit codes only.

### Residual risks

- **A service's own error text** (FinMind's `msg`, an error body of spylead or ibguard) is copied into `SourceError` and so into events and `last_fetch_error`. Were a service to echo the credential in its message, `redact` would not mask it, since it matches `key=value` and header patterns, not bare values. Masking the configured secret values literally in `SourceError` text would close it.
- **The session value** stays valid after logout until the web token changes (see §2).
